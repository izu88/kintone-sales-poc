# 応募・面談向け説明

## このPoCを一言で説明する

BtoB営業の問い合わせ受付を題材に、Web問い合わせをn8nで受信し、Difyで要約・カテゴリ分類・顧客課題抽出・次回アクション生成を行い、その結果をkintoneへ自動登録するE2E業務改善PoCです。

単に正常系をつなぐだけでなく、入力不備、Dify停止、kintone API失敗を分岐し、HTTP 400 / 502として返すところまで実機検証しています。

## 30秒版

営業問い合わせの転記と初動整理を自動化するPoCを作成しました。n8nでWebhookを受け、Difyで問い合わせを要約・分類し、顧客課題と次回アクションまで生成してkintoneへ登録します。正常系だけでなく、必須項目不足、AIサービス停止、kintone API失敗までエラーハンドリングを入れ、E2Eで検証しています。

## 90秒版

想定した課題は、Web問い合わせ後に担当者が内容を読み、Excelや管理ツールへ転記し、初回対応に必要な情報を整理している状態です。

そこで、問い合わせ受付をn8nのWebhookに集約し、必須項目を検証した後、Dify Workflow APIへ問い合わせ本文を送る構成にしました。Difyでは、問い合わせ要約、カテゴリ分類、顧客課題抽出、次回アクション生成を行い、n8n側で元の問い合わせ情報と統合してkintoneへ登録します。

実装時は、DifyのStructured Outputを利用した際に利用モデルとの組み合わせで期待どおり値が取得できないケースがあったため、Code NodeでLLMのJSON出力を解析するフォールバックを入れました。また、Dify停止時にn8n全体が500で終了しないようError Outputへ分岐し、502を返す設計にしています。

最終的に、正常登録、必須項目不足400、Dify停止502、kintone API失敗502まで実機確認しました。認証情報はn8n Credentialsへ分離し、共有用Workflow JSONでは実サブドメインやCredential参照も除去しています。

## このPoCで示せること

- 業務課題をAs-Is / To-Beへ整理し、実装単位へ落とし込む
- kintone標準機能、JavaScript、REST APIを組み合わせる
- n8nでWebhook受付、入力検証、API連携、分岐処理を構築する
- DifyでAI処理を独立したWorkflowとして設計する
- AI出力を業務データへマッピングする
- 外部API障害を想定したエラーハンドリングを実装する
- 認証情報をWorkflow本体から分離する
- 正常系と主要な異常系を実機テストする
- PoCをREADME・設計資料・スクリーンショット・再利用可能なWorkflowとして整理する

## 技術選定を聞かれたとき

### なぜkintoneか

営業案件のような業務データを、フォーム・一覧・プロセス管理などの標準機能で短期間に構築できるためです。標準機能で不足する箇所だけJavaScriptやREST APIで補完する構成にしました。

### なぜn8nか

Webhook受付、入力検証、外部API呼び出し、エラー分岐といった連携処理をWorkflowとして可視化しやすく、業務フロー変更にも追従しやすいためです。

### なぜDifyを分けたか

今回の処理はn8n単体でも実装可能です。一方、AI処理をDifyへ分離すると、プロンプトやモデル設定を連携ロジックから独立して管理でき、将来的なRAG追加や別Workflowからの再利用もしやすくなります。その分離パターン自体を検証対象にしました。

## トラブル対応を聞かれたとき

### Structured Outputで値が取れなかった

利用モデルとの組み合わせで、DifyのStructured Outputを直接参照すると期待どおり値が取得できないケースがありました。LLMのJSON文字列をCode Nodeで解析し、必要な4項目へ変換するフォールバックに切り替えました。

### Dify停止時に500になった

HTTP Requestの通信エラーでWorkflow自体が停止していたため、On Errorを `Continue (using error output)` に変更し、Error Outputを502レスポンスへ接続しました。

### ローカル環境が重くなった

16GB Mac上でDifyとn8nを同時起動した際、Rancher Desktopの初期割当では応答が停滞しました。2 CPU / 約4GBから4 CPU / 約8GBへ変更し、統合テスト時だけ両方を起動する運用にしました。

## 面談で誤解を避けるポイント

この成果物は実案件の本番導入実績ではなく、自主PoCです。実測の工数削減率や売上改善率はまだありません。そのため、成果は「本番効果」ではなく、要件整理、設計、実装、障害系を含む検証、ドキュメント化まで一連で行ったこととして説明します。
